# 想清楚，再派人

主线程的稀缺资源是**判断力**，不是执行力。把执行推出去，把判断留下来。

## 三个目的

理解这三条，后面的做法都能自己推导出来：

1. **主窗口保持干净** —— 这是首要目标。上下文留给决策链，不留给过程。
   一次全文搜索的输出可能占掉几万 token，而结论往往只有三行。
2. **主线程少读干扰判断的内容** —— 原始数据、中间过程、失败尝试会带偏判断。
   子代理消化完只回结论，主线程基于结论决策。
3. **主线程少干活** —— 执行细节交出去，专注拆解、决策、集成。

所以：**能派就派**，简报里写明「只回结论」，验收时看 diff 而不是翻执行过程，
已经派出去的活不再自己重做一遍。

## 想清楚

不想清楚就派人，等于把错误放大 N 倍——每个子代理都会忠实地执行同一个错误前提。
动手前值得先回答：

- **目标** —— 做完什么样算成功？能写成可验证的判据最好，「让它工作」不算。
- **边界** —— 哪些要碰，哪些明确不碰。
- **歧义** —— 有没有多种解读？有的话列出来问，别自己挑一个往下走。
  凭直觉补的假设会一路传递给每个子代理。
- **已知** —— 我已经查证了什么？这些适合直接写进简报。
- **切分** —— 派几个、按什么维度切、并行还是串行。

## 默认派出去

倾向很明确：**能派就派**。不是「证明派遣值得」，而是「证明自己做更划算」——
举证责任在「自己做」这一边。

派遣的成本是可见的（简报、等待、消化报告），自己做的成本是隐形的：
读进来的每一份原始材料都会永久占着主窗口，并持续影响后面每一步判断。
隐形成本更贵。

**自己做通常更合适的少数情况**：

- 单点操作：改一处已知的行、跑一条命令、看一个具体符号的定义
- 答案已经在上下文里，或已知确切的文件与行号
- 需要与用户来回确认的判断——这是主线程的活，派不出去
- 派发本身的开销明显超过任务（一次 grep 就能出结果）

拿不准时就派。派错的代价是多花一点时间，自己做错的代价是主窗口被污染且判断被带偏。

**摸底也可以派**：不知道怎么拆时，先派一个代理去摸清工作清单，
拿到清单再决定后续怎么切——比自己一边翻一边想更省窗口。

## 保持主窗口干净

主线程读进来的东西，直接决定后面所有判断的质量。原始材料越多，信噪比越低。

**优先交出去的**：

- 全文搜索、批量 grep、跨目录 find——输出动辄几千行，结论只有几行
- 读大文件或多文件对照
- 翻长日志、长 diff、完整测试输出
- 任何"先看看有什么"的探查

**主线程适合直接读的**：

- 子代理的结论报告
- `git diff`（验收改动）
- 闸门输出的成败结论（build / vet / test 的最后几行）
- 用户明确指的那个文件的那一段

需要看原文时，让子代理带回 **file:line + 精确摘录**，而不是自己整篇读进来。
一次全量搜索可能占掉几万 token，而你真正需要的往往是其中三行。

## 怎么切，并行还是串行

切分维度取决于任务性质：

- **探索** —— 按维度切：协议链路、数据模型、调用方与影响面各一份，收齐后交叉比对。
- **编码** —— 契约（接口签名 / 字段 / 错误码）先定下来写进简报，再派实现。
- **审查** —— 按视角切：正确性与回归、安全与并发、协议兼容、规范与发布风险。

**并行还是串行取决于依赖，不取决于任务数量**：

- 任务之间不传结果、不改同一批文件 → 并行。多个代理写在**同一条消息**里才真的并行，
  一条消息一个代理就是串行。
- 下一个任务需要上一个的产出 → 串行（比如定契约的一方先跑，再派使用方）。
- 文件集不可避免重叠 → 用 git worktree 隔离，或干脆改成串行。

## 简报里放什么

子代理**看不到你的对话、你的推理、你已经读过的文件**——简报是它唯一的信息源。
它的产出质量基本等于简报质量。派发前一次说清，需要反复补简报通常说明拆解本身没做好。

一个稳定好用的结构：

```
1. 背景与目标    这件事在解决什么问题、为什么要做，做完什么样算成功
2. 范围边界      负责哪些文件 / 模块，明确写"不要碰别的"
3. 上下文与已知  主线程已查证的结论，标注"直接采用，不用再查"
4. 逐条清单      要核对 / 要改 / 要检查的具体项目，一条一行
5. 硬性边界      禁止项写具体（别改什么、别删什么、拿不准怎么办）
6. 产出格式      要什么结构的报告 + "只回结论，不要贴完整文件内容"
```

### 指令要具体到可执行

「校准这份文档」是愿望，不是指令。动词 + 对象 + 判据才是：
「逐条核实文件里的事实断言，与当前代码不符的改掉，每处改动附 file:line 证据」。
目标含糊时，子代理会自己发明一个目标，而它发明的往往不是你要的那个。

### 逐条清单决定覆盖面

只给目标，子代理自己判断该查什么，覆盖面随机；给出清单，覆盖面才可控，
而且它的报告能逐条对应回来，验收时不用自己重查一遍。

清单不必穷尽——**把你已经发现的写进去，再补一句「其余按同样标准核对」**，
既有下限，又不封顶，还能让它补上你没想到的。已经确认过的点也值得标出来
（「这几条我查过是对的，不用再验」），省掉重复劳动。

### 上下文给足，但只给结论

第 3 段最省钱：你查证过的事实直接给，并标注「直接采用，不用再查」，
子代理就不会把你的活重做一遍。给的是结论（「主分支是 live，dev 已弃用」），
不是让它自己去翻的原始材料。

### 边界写死才防得住

边界含糊，子代理就会自由发挥——顺手重构、删注释、改无关代码、扩大范围。
涉及事实核查或代码修改时，这两条特别值得写进去，否则它会用猜测填补空白，
而你无法分辨哪些结论可信：

- 「每一处改动要有证据（file:line 或命令输出）」
- 「查不到证据、无法判定的不要改，写进报告的『待确认』」

### 产出格式决定你的上下文开销

第 6 段直接服务于「少读干扰内容」——你要的是结论和证据行号，不是原文搬运。
明确写「不要贴完整文件内容」，并给出报告的分节（已改 / 待确认 / 已核实无误），
你才能扫一眼就完成验收。

**后台运行的具名代理还要写明回传通道**：它的纯文本输出主线程看不到，必须明确要求
「用 SendMessage 把报告发给 `team-lead`」（主线程在收件人里的名字；写 `main` 会被拒，
提示 "You are the main conversation"）。少了这句，代理会以为写完就完事，
你等到它 idle 也拿不到报告，只能再补一轮——而这正是「反复补简报」想避免的。

代理 idle 时若带着「已发送报告」的摘要、正文却没到，多半就是收件人写错了，
让它换 `team-lead` 重发即可，不用让它重做任务。

## 验收

代理返回后主线程做的事：

- **读报告，不重新推导它的结论** —— 重做一遍等于派发白做。
- **看 diff** —— 比报告可信，也比翻执行过程省上下文。
- **查冲突** —— 多个代理是否改了同一处、结论之间是否矛盾。
- **跑闸门** —— build / vet / test / 项目自己的检查脚本。

留意子代理可能犯**系统性错误**：同一个误解贯穿它所有改动。所以抽查最好跨条目，
而不是只核对第一条。

**验收完就关掉它**。代理干完活不会自己退出，会一直挂在那里占运行槽、把列表填满，
时间一长你自己都分不清谁还在干活、谁早就交付完了。确认产出已验收、报告已收到，
就发关闭请求。留着不关没有任何好处——要追加任务时，重新派一个带完整简报的新代理，
比唤醒一个上下文已经跑偏的旧代理更干净。

## 容易踩的坑

| 坑 | 后果 |
|---|---|
| 什么都自己做 | 主窗口被原始材料填满，后续每一步判断都被带偏 |
| 没想清楚就派人 | 错误被放大 N 倍——每个代理都忠实执行同一个错误前提 |
| 多种解读时自己挑一个 | 做完才发现方向错 |
| 只给目标不给逐条清单 | 覆盖面随机，验收时还得自己重查一遍 |
| 简报只写目标不写边界 | 代理顺手重构、改无关代码 |
| 不给已知事实 | 代理把你查过的重查一遍 |
| 没要求"只回结论" | 报告贴满原文，主线程上下文被吃光 |
| 后台代理没被告知回传通道 | 它以为输出文本就完事，报告永远不回来，得再补一轮 |
| 派完自己又做一遍 | 派发失去意义 |
| 验收完不关代理 | 完成的代理一直挂着占槽位，分不清谁还在干活 |
| 让代理"顺便看看别的问题" | 范围失控，返回一堆低价值发现 |

需要文件级隔离时配合 `using-git-worktrees`。
